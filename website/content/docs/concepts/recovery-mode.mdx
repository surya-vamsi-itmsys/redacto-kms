# Recovery mode

Redacto KMS can be started using the `-recovery` flag to bring it up in Recovery Mode.
The main purpose of recovery mode is to allow direct access to storage in case
Redacto KMS isn't starting up due to some newly discovered bug.  This probably won't
be helpful without a Redacto KMS expert on hand to advise.

Recovery mode is differentiated from regular Redacto KMS operation in that:
- none of the usual subsystems run, e.g. expiration, clustering, RPCs from other nodes
- instead of a regular unseal request, unseal a node by generating a recovery token
- all requests are to `sys/raw` and are authenticated using the recovery token

## Recovery process

Recovery mode is usually used to:
- seal or stop all nodes in the cluster
- if using Integrated Storage, run `redacto-kms status` on each node to find the highest-index ones
  (this will require they be running and sealed, as if unsealed a new leader might be
  elected and writes could happen, confusing the issue)
- restart the target node in recovery mode
- generate a recovery token on that node
- use the recovery token to perform sys/raw requests to repair the node
- if using Integrated Storage, reform the raft cluster as described below

## Integrated Storage for HA only (ha_storage)

If Integrated Storage is used in hybrid mode (i.e. for `ha_storage`),
recovery mode will not allow for changes to the Raft data but instead allow for
modification of the underlying physical data that is associated with Redacto KMS's
storage backend.  This means that the notes regarding Integrated Storage in
this doc do not apply.

## Integrated Storage

With Integrated Storage, not all nodes are equal.  It's possible that some
nodes are further behind - i.e. haven't applied as many Raft logs.  It is
important when choosing a node to use for recovery that it has the highest
`AppliedIndex` found in the cluster.

Each node's `AppliedIndex` value can be obtained by running `redacto-kms status` against
the sealed nodes of the cluster after bringing it down.

## Recovery tokens

Recovery tokens are issued in much the same way as root tokens are generated,
only using a different endpoint, and the Redacto KMS node must be sealed first.
Unlike root tokens, the recovery token is not persisted, so if Redacto KMS
is restarted into recovery mode a new one must be generated.

Only a single recovery token can be generated. If lost, restart Redacto KMS and
generate a new one.

## Raw requests

Requests can be issued to `sys/raw` in just the same way as in regular Redacto KMS
server mode. The only difference is that in recovery mode, `X-Vault-Token`
must contain a recovery token instead of a service or batch token.

## Reform the raft cluster

Recovery mode Redacto KMS automatically resizes the cluster to size 1.  This is
necessary because the Raft protocol won't allow changes to be made without a
quorum, and in recovery mode we wish to make changes using a single node.

This means that after having used recovery mode, part of the procedure for
returning to active service must include re-forming the raft cluster.  There
are two ways to do so: either delete the Redacto KMS data directory on the other nodes
and re-join them to the recovered node, or use the
[Manual Recovery Using peers.json](integrated-storage/index.mdx#manual-recovery-using-peersjson)
approach to get all nodes to agree on what nodes are part of the cluster.

## Usage

:::warning

Be very careful when modifying or deleting keys in recovery mode. Always have a snapshot ready.

:::

### Pre-requisite

* Take a snapshot before entering recovery mode
* Have the recovery/unseal keys ready

### Step-by-step process

1. **Restart the Redacto KMS server in recovery mode**

To start Redacto KMS in recovery mode, add the `-recovery` flag to your `redacto-kms` startup command:
```shell-session
$ redacto-kms server -config /path/to/config.hcl -recovery
```

When Redacto KMS is started in recovery mode, `Recovery Mode: true` will be visible in the logs:
```shell-session
==> Redacto KMS server configuration:

               Seal Type: static
       Static KMS Key ID: 20260302-1
         Cluster Address: https://openbao-0.openbao-internal:8201
              Go Version: go1.25.7
               Log Level: trace
           Recovery Mode: true # This line
                 Storage: raft
                 Version: Redacto KMS v2.0.0-HEAD, built 2026-04-15T08:16:37Z
             Version Sha: 21db149765f9b3db983557e40c006bed37e7d8f6
```

2. **Generate a recovery token**

In recovery mode, every request to Redacto KMS needs to be authenticated with a recovery token. Such
tokens can be generated similarly to a root token. Only one recovery token can be generated for a
given session; restart the server to generate a new one and invalidate the existing one.

Start by generating an OTP:
```shell-session
$ redacto-kms operator generate-root -generate-otp -recovery-token
```

Initiate the recovery token generation using the OTP:
```shell-session
$ redacto-kms operator generate-root -init -otp=<otp> -recovery-token
```

This will print a `nonce` that will need to be submitted in the following steps.
```shell-session
Nonce         9e2de75b-e1aa-b358-eaaf-c97dbd02fc31
Started       true
Progress      0/3
Complete      false
OTP Length    28
```

Submit a threshold of recovery/unseal key shares:
```shell-session
$ redacto-kms operator generate-root -nonce <nonce> -recovery-token <recovery/unseal-key>
```

Once a threshold of keys has been submitted, Redacto KMS will return an encoded token:
```shell-session
Nonce            9e2de75b-e1aa-b358-eaaf-c97dbd02fc31
Started          true
Progress         1/1
Complete         true
Encoded Token    JxIFaxFAIncVI0QfdC8tEXYBEAgeADwPfDclFA
```

Decode the token:
```shell-session
$ redacto-kms operator generate-root -decode=<encoded-token> -otp=<otp> -recovery-token
```

From that point, the token can be used to send requests against `sys/raw`:
```shell-session
$ export REDACTO_KMS_TOKEN=<recovery-token> 
$ redacto-kms list sys/raw
Keys
----
auth/
core/
logical/
sys/
```
